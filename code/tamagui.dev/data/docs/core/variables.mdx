---
title: Variables
description: Redefine theme values for any part of the tree
---

Set theme values directly on `<Theme>` to patch them for a subtree, the same
way CSS custom properties let you redefine `--x` on any node. Listed keys
override, everything else inherits from the parent theme. No named theme, no
config change.

## Usage

```tsx
import { Theme, View } from 'tamagui' // or '@tamagui/core'

export default () => (
  <Theme background-hover="blue4 dark:blue2">
    <View backgroundColor="background hover:background-hover" />
  </Theme>
)
```

Values use the same flat grammar as style props, so `dark:blue2` here means
what it means everywhere else. `<Theme>` applies its values to a whole
subtree rather than to one element, so only the modifiers that make sense for
a subtree work:

- **Theme:** `dark:`, `light:`, or any of your theme names. Matching follows
  theme nesting, so `blue:` applies under `dark_blue`, `light_blue`, or a
  theme named `blue`.
- **Platform:** `ios:`, `android:`, `web:`, `native:`.

Interaction states (`hover:`, `press:`) and media queries (`sm:`) describe an
element, not a subtree, so they warn in development and are dropped.

A `name` and inline values compose, and cost one node either way:

```tsx
<Theme name="dark" background="red">
  {/* dark, with background overridden */}
</Theme>
```

Keys must be theme keys, or custom variables you declare in your config
(below). Unknown keys warn in development and are dropped, which keeps web and
native behavior identical since native resolves values in JavaScript. The
props `<Theme>` already owns (`name`, `reset`, `debug`, `forceClassName`,
`shallow`, `className`, `children`, `passThrough`, `contain`) can't be used
as theme keys. Tamagui reports a collision in development.

## Custom variables

Declare your own variables in `createTamagui`. They merge into your base
themes, so they work everywhere theme keys work: style props, `useTheme()`,
and `<Theme>` redefinition.

```tsx
const config = createTamagui({
  // ...tokens, themes
  variables: {
    surfaceBorder: 'border-color', // reference a theme key
    disabledOpacity: 0.5,
    focusRingColor: 'blue10',
    focusRingWidth: 2,
    pressScale: 0.97,
    // per-scheme values
    accent: { light: '#005ac8', dark: '#78b4ff' },
  },
})
```

Then use them like any theme value, and redefine them per area:

```tsx
<View borderColor="surfaceBorder" />

<Theme surfaceBorder="red8">
  {/* everything here sees the red surface border */}
</Theme>
```

This is the intended home for design-system conventions that used to be
copied into every component: focus rings, disabled treatments, press
feedback, easing names. Define them once at the root, read them from your
copied component styles, and redefine them per section when a marketing page
or a dense settings panel wants a different feel.

## References

Values can reference theme keys and tokens:

- `background` finds the theme key (or custom variable) visible at the
  `<Theme>` node.
- `size.4` and `color.blue10` reference tokens by category.
- A bare token name like `blue10` checks theme keys first, then scans token
  categories in a fixed order: color, space, size, radius, zIndex. Use the
  qualified form if a name exists in more than one category.

References resolve at the `<Theme>` node and descendants inherit the resolved
value, matching how CSS computes custom properties. Chains are fine (`a: 'b'`
where `b: 'c'`), but there is no `calc()`-style computation, and a reference
cycle drops the involved keys entirely on both platforms with a development
warning.

## Units

Numbers become `px` on web and stay numbers on native, the same as numeric
style props. Keys that end in `opacity`, `scale`, `zIndex`, `weight`, `flex`,
`grow`, `shrink`, `ratio`, or `elevation` stay unitless. For explicit pixel
values use a `"10px"` string or the `px(10)` helper; native receives the
number either way.

## Nesting

Inline values stack, with the nearest definition winning per key. A `<Theme>`
that resolves a new theme name resets whatever keys that theme defines,
exactly like nesting themes has always worked; if a patch should survive a
theme switch, put it inside. Custom variables are only defined on base themes,
so sub-themes like `level2` inherit your patches rather than resetting them.

## What it costs

Changing inline values leaves unrelated descendants alone. Tamagui tracks
which theme keys each component reads, so only components that actually read
a changed key do any work. Both platforms use the same tracking as an ordinary
theme change.

On web, styled components skip even that: the values compile to CSS custom
properties on the `<Theme>` node, so they restyle through the cascade with no
JavaScript at all. JavaScript readers (`useTheme().key.val`, animation
drivers) still see the patched values, on both platforms, because that is the
point of them. On iOS with `settings.fastSchemeChange`, patched keys whose
light and dark values are both literals keep the no-re-render scheme flip via
`DynamicColorIOS`.

## Migrating from `<Variables>`

The `<Variables>` component is deprecated. Its two objects collapse into props,
and its `themes` map becomes the theme modifier:

```tsx
// before
<Variables values={{ 'background-hover': 'blue4' }} themes={{ dark: { 'background-hover': 'blue2' } }}>

// after
<Theme background-hover="blue4 dark:blue2">
```
