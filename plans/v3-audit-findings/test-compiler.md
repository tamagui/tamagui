# BUILD-TIME v3 testing and validation gaps

## Summary

- **F1 is the highest-value gap.** [READ] The repository has useful compiler/runtime-internal parity tests, but no test that renders the same authored tree through the uncompiled runtime and the compiler in a browser and compares the resulting styles. The existing precedence corpus explicitly skips runtime comparison for `styled()` definitions. This would have caught the years-old `styled()` definition `transition` bug.
- [READ] The clause grammar has a real 2,000-case constructed fuzz and a 2,000-case chaos fuzz, but the canonical parser is not differentially checked against the duplicated scanners in `directStyle`, `propMapper`, and the lifecycle detector. Parser agreement is the cheapest high-yield addition here.
- [READ] `styleMode` is gone from active v3 source. The replacement is three package-selected frontends: regular Tamagui props, Tailwind class candidates, and DOM `style()` handles. Tailwind has the strongest frontend-specific tests. `to-tailwind` has only transform/round-trip tests, and there is no end-to-end browser parity matrix across all three frontends.
- [READ] Current zero-runtime hydration covers same-config mixed color spelling, an intentional render mismatch, and CSS round-trip controls. It does not cover theme selection changes, server/client media disagreement, request-specific values, RSC, or the standalone streaming test in CI.
- [READ] Metro and Next now compare cold and warm receipts. That close-out must not be re-reported as missing. The remaining determinism gap is a broad repeated-build/cross-machine check, especially for Vite and compiler artifacts.
- [READ] The requested test areas contain unconditional skips, a commented TODO test, and many assertions on emitted source strings. The latter validate implementation shape rather than browser/runtime behavior and are findings under the repository audit rules.

## Findings

### F1. No browser differential oracle for runtime versus compiled styles [high] [L] [READ]

- **Evidence:** I searched `code/compiler/static-tests`, `code/tests`, `code/kitchen-sink/tests`, and Vitest/Playwright configuration for `parity`, `computed`, `getComputedStyle`, `extractForWeb`, `renderToString`, `runtime`, and compiler output comparisons. A positive result would have used the same authored component tree twice, once through the ordinary runtime and once through compiled output, then compared a runtime style observation. I found no such broad browser test.
- **Evidence:** `code/compiler/static-tests/tests/flatValues.web.test.tsx:124-163` compares a clause class to `hostCore.getSplitStyles` and inserted runtime rules. That is useful, but it is an internal style-object/rule comparison, not two rendered trees. In the precedence corpus at `flatValues.web.test.tsx:223-299`, the `styledLayer` branch only checks that generated CSS contains declarations at lines 240-244. The runtime comparison is in the other branch at lines 245-272, and the scenario loop skips `styledLayer` at line 278.
- **Evidence:** `code/compiler/static-tests/tests/e2-parity.web.test.ts:159-180` compares compiler IR observations with frozen legacy observations. `code/core/tailwind/src/__tests__/parityShared.tsx:1-6,36-52,135-228` compares the Tailwind converter and shared resolver. Neither is runtime-versus-compiled browser equivalence.
- **Why it matters:** [INFERRED] A compiler decision made before later `completeProps` merging can diverge only when a value is authored in `styled()` static configuration. Internal rule tests can still pass while the browser result is wrong. The motivating `transition` and `runtimeAnimationProps` failure has exactly that shape.
- **Proposed change:** Add a browser differential harness. Render a runtime route and a compiled route from the same fixture, put stable `data-probe` markers on corresponding elements, and compare a canonical map from `getComputedStyle`. Compare CSS longhands rather than class names or emitted CSS text. This removes hash and rule-order differences and lets the browser expand shorthands and resolve variables. Normalize browser serialization, numeric zero forms, and whitespace. Do not compare class names. For stateful cases, drive the same hover/focus/media/viewport state before sampling; for transitions, use a dedicated fixture that samples the transition longhands and disables incidental animation.
- **Case generation:** [IDEA] Start with a hand-maintained corpus containing static `styled()` definitions, call-site props, style arrays, tokens/themes, media, pseudos, groups, dynamic bailout controls, and Tailwind candidates. Reuse the existing flat-value precedence fixtures. Later, generate cases from registered style properties, tokens, and modifier grammar. Arbitrary JSX generation is unnecessary and would create many cases the compiler is deliberately meant to bail out on.
- **Where and cost:** [IDEA] S is 1-2 days for a Vite/browser fixture with the first static slice. M is 3-5 days for a reusable fixture runner and 30-50 cases in `code/tests` or kitchen-sink. L is 1-2 weeks for Vite, Next webpack, and Metro web runs with persisted minimized counterexamples.
- **First slice:** [IDEA] Add three equivalent cases: `styled(View, { transition: 'medium' })`, a call-site `View transition="medium"`, and a plain runtime `View transition="medium"`. Compare `getComputedStyle(...).transitionDuration` and the other transition longhands. The definition case is the regression detector; the call-site case is the control that proves the harness can observe the property. This slice is small enough to ship before a general property generator.

### F2. Clause grammar fuzzing does not test agreement with the runtime scanners [high] [M] [READ]

- **Evidence:** The canonical grammar is `code/core/style-grammar/src/valueParser.ts:1-22,70-92,188-260`; it implements `value := base? clause*` and structured error spans. `code/core/style-grammar/src/__tests__/valueParser.test.ts:10-13,40-153,155-254,256+` covers ordinary values, functions, strings, clauses, and errors. `valueParser.fuzz.test.ts:212-253` constructs 2,000 valid/unregistered/invalid cases and `:318-333` runs 2,000 chaos strings for no-throw and malformed-output checks. `mergeFlatValues.test.ts:16-66,68-125` covers merge behavior, grammar-registry acceptance, and format/parse round trips.
- **Evidence:** There is one canonical full parser, but at least two duplicated full clause lexers. `code/core/web/src/helpers/directStyle.ts:1491-1528,1552-1669` scans quotes, nesting, whitespace, and top-level colons; its `getCondition` path is another condition/modifier parser at `:295-410`. `code/core/web/src/helpers/propMapper.ts:24-38,150-260` has a second top-level scanner. `code/core/web/src/hooks/useComponentState.ts:29-61` has a third, partial quote/depth/colon detector for lifecycle state. `getSplitStyles` delegates to these paths, but no test compares their token boundaries with `parseValue`.
- **Why it matters:** [INFERRED] Valid inputs can parse into one modifier/payload sequence in the canonical parser and a different sequence in a runtime scanner without either path throwing. Direct style also has an early return for top-level `;`, `{`, and `}` at `directStyle.ts:1572-1573`, while the canonical parser reports invalid characters at `valueParser.ts:221-260`. That is an untested error-contract divergence, not a confirmed user-visible bug.
- **Proposed change:** Add parser-agreement tests using the existing generated corpus. For each input, compare the canonical parser's base and ordered `(modifiers, payload)` clauses with the segments consumed by `directStyle` and `propMapper`. For valid values, assert identical boundaries, trimming, quote handling, escapes, and nesting. For invalid values, assert consistent rejection or the documented bailout. Exercise `hasFlatModifier` against the same inputs and assert it detects exactly the values with a flat modifier. The nearly-free oracle is agreement between implementations. The long-term fix is to route all three through a shared scanner/parser rather than maintain parallel lexers.
- **Cost:** [IDEA] S is about one day if the scanners expose test-only token traces or if the test calls existing segment helpers. M is 3-5 days to share the scanner and preserve diagnostics. L is 1-2 weeks to generate property-aware cases and run the agreement suite for web, native, compiler extraction, and Tailwind candidate conversion.

### F3. Frontend selection replaced `styleMode`, but coverage is uneven [medium] [M] [READ]

- **Evidence:** `rg` over active `code/` source found no `styleMode` setting or runtime branch. The only two code references are comments in `code/core/tailwind/src/__tests__/frontend.web.test.tsx:18` and `utilities.web.test.tsx:8`, both saying it is gone. The old documentation still says `settings.styleMode` at `docs/tailwind-mode.md:16-26`, and the release-state document repeats it at `docs/v3-beta-state-of-the-release.md:143`, so documentation is stale but this is not an active v3 mode count.
- **Evidence:** The replacement contract is documented at `plans/dom-tailwind-flat-values.md:238-270,1375-1387`: regular Tamagui props from `tamagui`/`@tamagui/core`, Tailwind class candidates from `@tamagui/tailwind`, and `style()` handles from `tamagui/dom`/`@tamagui/core/dom`, all lowering to shared property/value IR. `code/core/web/src/helpers/styleFrontend.ts:38-85,99-108` implements the descriptor seam and identity regular frontend. `code/core/tailwind/src/frontend.ts:10-110` implements the Tailwind descriptor; `compilerHost.ts:977-985` selects static normalization from imported component provenance without importing a frontend package.
- **Coverage by frontend:** [READ] Tailwind has web and native frontend tests. `code/core/tailwind/src/__tests__/frontend.web.test.tsx:285-390` covers styled-chain descriptor retention, static base/variant/compound normalization, passthrough ordering, package isolation, preprocessing idempotence, and untouched props. The native counterpart covers normalization and isolation at `frontend.native.test.tsx:205-208`. The package also has candidate, config-aware, round-trip, parity-gate, runtime-graph, and Vite suites. `code/core/to-tailwind` has only two test files, `distParity.test.ts` and `transform.test.ts`; `transform.test.ts` tests source-to-class conversion, including clauses and tokens, but it does not render a converted component or compare browser styles.
- **Coverage by frontend:** [READ] The regular frontend is covered indirectly by the compiler static tests and the broad core tests. The standalone DOM frontend has type isolation in `code/core/web/src/dom/standalone.test-d.ts:35-69` and compiler lowering tests in `code/compiler/static-tests/tests/domConformance.web.test.tsx:6-80`, but those tests inspect generated strings and CSS text. I found no three-way browser equivalence test proving that regular props, Tailwind class candidates, and DOM `style()` handles produce the same intended result for equivalent styling.
- **Why it matters:** [INFERRED] Package provenance is now the behavior switch, so a component crossing a package boundary or a `styled()` chain preserving the wrong descriptor can silently use the wrong syntax. Tailwind unit tests prove descriptor metadata and conversion, while DOM tests prove lowering shape, but neither catches a browser-visible mismatch against the regular frontend.
- **Proposed change:** Extend F1's corpus with three equivalent frontend fixtures for a shared subset: color, spacing, tokens, a flat hover clause, media, and theme. Assert equal computed longhands for regular `View`, Tailwind `View`, and standalone `html.div` where the contracts overlap. Add a provenance fixture that imports each component from its public package and chains `styled()` once. Keep frontend isolation and bundle-graph tests as separate structural checks.
- **Cost:** [IDEA] S is 1-2 days for a six-property web matrix. M is 4-6 days for web plus native resolver snapshots and `to-tailwind` converted-source fixtures. L is 1-2 weeks for compiler, SSR, and bundle-isolation coverage across all three frontends.

### F4. Hydration coverage proves one premise, not the important boundary variants [medium] [M] [READ]

- **Evidence:** `code/tests/zero-runtime/src/hydration.tsx:69-73` always renders `defaultTheme="light"`. `code/tests/zero-runtime/tests/vite-hydration.test.ts:42-82` covers same-config mixed spelling, an expected render-mismatch control, CSS round-trip equality, and a CSS round-trip mismatch control. The fixture captures `onRecoverableError` at `hydration.tsx:147-165` and records probe values, spellings, and colors.
- **Evidence:** [READ] I searched `code/tests/zero-runtime`, `code/tests/integration`, and `code/sandbox/tests` for RSC/server components, `matchMedia`, media emulation, request headers/cookies, random/date values, and readable-stream SSR. The zero-runtime hydration fixture contains no RSC, media-answer, theme-flip, or request-variant case. The sandbox CI job runs named SSR suites at `.github/workflows/checks.yaml:249-293`, but these are not a substitute for the zero-runtime compiler fixture's missing boundary cases.
- **What is covered now:** [READ] The stale `dist-hydration` false green was fixed in the close-out and must not be reported again. The current zero-runtime CI job builds and tests the fixture/starter on separate runners at `.github/workflows/checks.yaml:306-365`.
- **What is missing:** [READ] No case starts with server light markup and client dark theme selection, no case gives server and client different media answers, and no case renders a request-specific value that differs on the client. No RSC or React server-component test was found. The integration package has a separate streaming script, but its normal `test:web` is only the simple integration test (`code/tests/integration/package.json:8-17`).
- **Failure oracle:** [READ] Existing tests treat a nonempty `window.__hydration.recoverable` array, console error, or differing probe value as failure/control evidence. New cases should additionally assert final computed styles and DOM attributes. A theme/media/request mismatch should fail on `onRecoverableError` or an explicit probe mismatch, not merely on emitted CSS text.
- **Proposed change and cost:** [IDEA] Add theme-flip, server/client media disagreement, and deterministic request-value fixtures to the existing Vite hydration page. S is 1-2 days for the first three cases. M is 3-5 days for a matrix over Vite and Next. L is 1-2 weeks for RSC and streaming SSR in a real Next app-router fixture.

### F5. The streaming SSR test exists but is not wired into CI [medium] [S] [READ]

- **Evidence:** `code/tests/integration/tests/streaming.integration.test.js:7-19,58-108` is a browser proof that shell content paints before late content and that hydration has no errors. `code/tests/integration/package.json:17` exposes it only as `test:streaming`; `test:web` at line 9 runs the default integration command instead. I searched `.github/workflows/*` for `test:streaming` and found no workflow invocation. The unit-tests job at `.github/workflows/checks.yaml:133-137` runs `bun turbo run test:web`, so the separate script is not reached.
- **Why it matters:** [INFERRED] A streaming regression can leave ordinary SSR and zero-runtime hydration green while breaking the late-content or hydration ordering that this test was written to protect.
- **Proposed change:** Add the streaming integration command to the existing CI matrix, or make the default integration `test:web` include it with an explicit browser server lifecycle. Preserve the test's shell-before-late-content timing assertion and its no-hydration-error assertion.
- **Cost:** [IDEA] S is less than one day if the existing server setup is reliable; M is 2-3 days if CI needs a dedicated fixture server and artifact capture.

### F6. Cold/warm cache equality is covered for Next and Metro, but artifact determinism is not broad [medium] [M] [READ]

- **Evidence:** [READ] The close-out now compares cold and warm receipts. `code/tests/zero-runtime/scripts/metro-receipts.mjs:238-284` removes Metro cache, performs cold and warm builds, and checks scanned/reused state, identities, bridge data, and artifact bytes. `next-receipts.mjs:248-291` does the analogous Next check. Do not report this check as missing.
- **Evidence:** [READ] `code/compiler/metro-plugin/src/frontend.ts:426-460` validates options/source freshness and rehydrates CSS on cache hits. `compilerCache.test.ts:16-67` checks stable JSON/blob IDs, and `frontend.test.ts:420-443` checks concurrent same-cache output. I found no equivalent whole-artifact cold/warm byte comparison for the Vite receipts and no cross-machine or repeated-process determinism job.
- **Why it matters:** [INFERRED] The Metro plan-cache invalidation bug and stale-artifact false green show that cache provenance is part of the compiler result. A stable cache key can still hide nondeterministic CSS ordering, graph ordering, path metadata, or stale generated files in another integration.
- **Proposed change:** Add a same-input Vite cold/warm/repeated-process receipt. Compare CSS, extracted style graph, bridge manifests, and normalized emitted JS bytes. Canonicalize machine-specific absolute paths and source-map metadata before comparison, and keep raw bytes as a separate assertion for outputs that claim to be reproducible. Add one CI job on a second OS or runtime image for the normalized artifact set.
- **Cost:** [IDEA] S is about one day for Vite on one runner. M is 3-5 days for Vite, Next, and Metro normalized artifact manifests plus a second OS job. L is 1-2 weeks for hermetic toolchain/container validation and persisted diffs.

### F7. Source-string assertions and skipped tests leave behavior unverified [medium] [M] [READ]

- **Skipped or disabled tests:** [READ] `code/compiler/static-tests/bailoutMetric.web.test.tsx:61` is opt-in via `skipIf`; `babel.web.test.tsx:798-799` unconditionally skips the border-token case; `flatten.native.test.tsx:290-304` leaves a TODO test commented out. In `code/kitchen-sink/tests`, `ThemeMediaAnimation.test.tsx:4-5` skips an entire suite, `PopoverAnimatePosition.animated.test.tsx:9-12` skips a TODO setup case, and `MotionSSRHydration.animated.test.tsx:20-24` plus `CSSAnimationLifecycle.animated.test.tsx:5-9` skip driver subsets by design. I found no active `.only` or `.todo` modifier in the requested compiler, grammar, Tailwind, to-Tailwind, zero-runtime, Next, or kitchen-sink test directories. The conditional driver skips are still worth tracking in coverage reports, but the unconditional suite and TODO skips are direct gaps.
- **Source-string assertions:** [READ] Compiler tests repeatedly assert emitted source with `toContain`, `toMatch`, or exact code equality. Examples include `domConformance.web.test.tsx:17,40`, `moduleFormat.web.test.tsx:50-77,106,200-203`, `e3-lowerer.web.test.ts` multiple `output.code` assertions, `styled.web.test.tsx:39,169`, `flatValues.web.test.tsx:126,129,167-180,197-200,220-221`, `flatten.native.test.tsx:88,170,189-190,208-209,225,243,265-266`, `themedFlatten.native.test.tsx:192,243,383`, and `domPlatformFixture.test.tsx:43-45`. Next tests do the same in `code/tests/next-webpack/tests/platform-specific.unit.test.ts:48-225`, `exports.unit.test.ts:42-75`, and `code/tests/next-turbopack/tests/turbopack.test.ts:57-60,75-78`. Zero-runtime receipt scripts use emitted JS/CSS `includes()` at many sites, including `zero-receipts.mjs:76,94-95,111-114,139,270,275-277,354,439-440,498-499,578-588,647,804,826+`, with analogous checks in `next-receipts.mjs` and `metro-receipts.mjs`.
- **Why it matters:** [INFERRED] These assertions can remain green when a class hash, import path, emitted helper, or CSS spelling changes while the browser style is wrong. They also encourage tests to preserve compiler implementation shape instead of testing the compiler contract. The repo's own audit rule says source-string assertions are worthless, so each is a finding even when it guards a currently useful implementation detail.
- **Proposed change:** Replace behavior assertions with browser computed-style or native style observations wherever the contract is visual or runtime. For graph/isolation guarantees, inspect parsed module graphs or AST imports rather than source substrings. Keep a small number of structural assertions only when the exact AST property is the product contract, and make those assertions parse the output instead of searching text. Track every unconditional skip with an owner, issue, and CI-visible reason; either restore `ThemeMediaAnimation` and the border-token case or remove them from the claimed coverage.
- **Cost:** [IDEA] S is 1-2 days to remove the most dangerous string checks around flat values and DOM lowering. M is 1-2 weeks to migrate the compiler, Next, and zero-runtime receipts to structured/runtime oracles. L is 3+ weeks for the full static-test corpus and cross-target browser coverage.

## Ideas

- [IDEA] Persist minimized differential failures as fixtures containing authored JSX, target, config, expected normalized computed-style map, and compiler diagnostics. This turns a random generated case into a permanent regression test without freezing class hashes.
- [IDEA] Make the frontend matrix a shared data table. Each row names the equivalent regular, Tailwind, and DOM `style()` authoring forms plus the targets on which the forms are valid. This prevents Tailwind and DOM tests from silently drifting apart.
- [IDEA] Report parser-agreement coverage separately from parser branch coverage. A parser can execute every branch and still disagree with a second scanner at one quote or nesting boundary.
