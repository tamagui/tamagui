# cleanup / compiler toolchain audit

## Summary

- The Rust LSP has a second flat-value parser and modifier vocabulary. It already disagrees with the canonical `@tamagui/style-grammar` used by the TypeScript compiler, language service, and ESLint rule.
- Native DOM lowering has a new silent-drop class: `onBeforeInput`, `onInvalid`, and `onSelect` are consumed after a non-blocking structural diagnostic and are emitted nowhere.
- Vite, Next, Metro, and webpack loader each repeat compiler-project loading and zero-runtime `outputCSS` policy. Their resolver-specific work belongs at the edge; project normalization belongs in one static/compiler entry point.
- Build-time evaluation still has recovery at the failure site. `registerRequire` replaces failed modules with a proxy, and the webpack plugin silently drops unresolved configured component aliases unless debug logging is enabled.
- Metro's user-facing diagnostics discard the compiler source span, and ordinary compiler parse errors have no line or remediation. The TypeScript language service and ESLint rule are otherwise on the shared grammar path.

## Findings

### F1. Rust LSP owns a drifting second clause grammar [high] [large] [READ]

- Evidence: `code/lsp/crates/tamagui-grammar/src/lib.rs:1-6` says the Rust grammar is intended to back the language server “the way `@tamagui/style-grammar` does.” It nevertheless has its own parser in `code/lsp/crates/tamagui-grammar/src/value.rs:95-173` and its own hard-coded modifier table in `code/lsp/crates/tamagui-grammar/src/vocab.rs:57-62`.
- The canonical implementation is different. `code/core/style-grammar/src/stateModifiers.ts:1-24` spells the interaction modifiers `focus-visible` and `focus-within` and aliases `active` to `press`. `code/core/style-grammar/src/modifierRegistry.ts:45-54` adds aliases and component states, `:99-109` owns group modifiers, and `:124-145` owns container modifiers. The Rust table only contains camelCase `focusVisible`/`focusWithin`, has no `active` alias, and has no equivalent group/container/component-state registry.
- The Rust parser treats every depth-zero colon as a modifier boundary (`value.rs:155-160`) and its diagnostics validate against the Rust vocabulary (`lib.rs:101-145`). LSP call sites use this implementation directly in `code/lsp/crates/tamagui-lsp/src/features.rs:14,79,164,260,308`. This means editor acceptance/completion can differ from compiler lowering for the same value.
- Why it matters: a value can be accepted or completed by the editor using one spelling and then be classified differently by the compiler. This is a correctness and maintenance split, not merely a presentation difference.
- Proposed change: make `@tamagui/style-grammar` the one semantic source. If the native LSP cannot consume TypeScript directly, generate the modifier registry, aliases, parameterized-modifier rules, and conformance vectors from that package and make the Rust parser pass those vectors. Keep Rust only as an editor transport/parser implementation, never as a second owner of clause meaning.
- Risk / what could make this wrong: the Rust parser may intentionally be a tolerant editor tokenizer rather than a validator. That does not explain the explicit “same engine” contract or the Rust diagnostics/vocabulary owning semantics. A native implementation is acceptable only if its behavior is generated and conformance-tested against the canonical registry.

### F2. Native DOM events can be consumed and emitted nowhere [high] [medium] [READ]

- Evidence: `code/compiler/static/src/domStructuralPass.ts:91-113` recognizes DOM event props from the shared `EVENTS` table and records a `local/unsupported-prop-key` diagnostic when `row.native === 'none'`. The diagnostic is created with `localBailout`, which does not set `blocking` (`code/compiler/compiler-core/src/diagnostics.ts:82-88`).
- The same entries are then consumed by native lowering. `code/compiler/static/src/compilerHost.ts:730-741` calls `consume(entry)` for every event with `event.native === 'none'` and continues without an edit or addition. The final consumed entries are merged into `styleEntries` at `compilerHost.ts:2095-2104`, so the source prop is removed from the output. The affected table entries are `onBeforeInput`, `onInvalid`, and `onSelect` at `code/core/dom/src/tables/events.ts:150-173`.
- Zero mode cannot catch this path either: `code/compiler/compiler-core/src/zero.ts:162-170` only turns blocking diagnostics into violations. The normal webpack loader returns transformed code and does not surface `extracted.plan.diagnostics` (`code/compiler/loader/src/loader.ts:102-128,190-207`).
- Why it matters: a handler is accepted by the DOM contract, then silently disappears from native output. The structural pass has evidence of the problem, but the lowering pass treats the same prop as safely consumable and the ordinary adapter drops the evidence.
- Proposed change: keep unsupported native events on the runtime path, or make the structural diagnostic blocking before native lowering can consume the entry. If the intended contract is deliberate dropping, emit a diagnostic that names the prop and replacement (`onFocus`, a ref, or a platform guard as appropriate). Add one behavioral native compile test per affected event that checks both output and diagnostic delivery.
- Risk / what could make this wrong: the runtime may deliberately accept these props as no-ops on native. Even then, consuming them is still a silent source transformation. The result should either preserve the prop for the runtime/no-op policy or report the platform-specific drop; it should not have both a discarded non-blocking diagnostic and an erasing lowering.

### F3. Four integrations repeat project loading and zero-runtime policy [medium] [large] [READ]

- Evidence: all four adapters independently decide how to load the compiler project and when to remove config-only CSS:
  - Vite evaluates modules and calls `Static.loadTamaguiFromModules`, with its own zero-mode `outputCSS: undefined` condition at `code/compiler/vite-plugin/src/loadTamagui.ts:151-181`.
  - Next's webpack loader calls `Static.loadTamagui` for the global CSS tier at `code/compiler/loader/src/TamaguiPlugin.ts:83-95`, and repeats the zero-mode project load and `outputCSS: undefined` at `:130-143`.
  - The webpack transform calls `Static.loadTamagui`, repeats the same zero override, and independently resolves `['@tamagui/core', ...components]` at `code/compiler/loader/src/loader.ts:84-101`.
  - Metro repeats the load and zero override at `code/compiler/metro-plugin/src/frontend.ts:570-588`, then independently resolves every project component at `:589-610`.
- Next and Metro also duplicate build-config merge/normalization (`code/compiler/next-plugin/src/withTamagui.ts:40-45` and `code/compiler/metro-plugin/src/index.ts:79-90`), while Vite has a third async variant at `code/compiler/vite-plugin/src/loadTamagui.ts:73-82`. The adapters therefore have multiple answers to which options, platform, component set, and zero mode define one compiler project.
- Why it matters: a policy change has to be made in several adapters, and the existing code already demonstrates divergence in sync/async loading, component resolution, and whether `outputCSS` is removed for report versus enforce. A new integration can silently get a different compiler project from the existing ones.
- Proposed change: add one static/compiler-owned `loadCompilerProject` entry point that accepts the resolved target/root/options and returns evaluated config, component modules, project generation, and the zero CSS policy. Adapters should supply only resolver/evaluation hooks and bundler-specific artifact/gate work. Keep the shared `Static.CompilerFrontend` as the lowering owner.
- Risk / what could make this wrong: Vite's ModuleRunner, webpack's resolver, and Metro's resolver must remain adapter-owned. The proposal does not move resolution into static; it centralizes the normalization and project contract after each adapter resolves modules. The already-shared `CompilerProject` shape is the natural boundary.

### F4. Evaluation failures are converted into successful-looking partial builds [high] [medium] [READ]

- Evidence: `code/compiler/static/src/registerRequire.ts:202-232` catches every failed `require`, returns `proxyWorm`, and suppresses the warning unless `TAMAGUI_SHOW_FULL_BUNDLE_ERRORS` or `DEBUG` is set (`:213-228`). The file explicitly says the proxy is used to keep reading config/components after external modules fail (`:223-225`). This is recovery at the evaluation failure site, not a lowerer declining an unsupported style.
- The webpack integration has a second silent recovery chain. `code/compiler/loader/src/TamaguiPlugin.ts:316-337` catches failed `requireResolve` calls in `safeResolves`, silently omits the entry, and logs only under `DEBUG`. `componentsFullPaths` feeds that result at `:340-347`, and `isInComponentModule` uses the reduced list at `:364-368`. A typo or unavailable configured component can therefore change component-module classification without a normal diagnostic.
- `code/compiler/compiler-core/src/lower.ts:297-321` catches any exception from `host.lowerCandidate` and converts it to `local/style-resolution-failed`. A lowerer returning `ok: false` is a legitimate designed tier: the source remains on the runtime path. Catching arbitrary exceptions and then letting ordinary adapters ignore plan diagnostics is different; it hides implementation defects as ordinary extraction declines. The distinction is visible in the code, but the adapters do not preserve it for users.
- Why it matters: config/component evaluation is the input to the compiler, so proxying or omitting failed inputs can produce incomplete static configs and partial extraction. A lowerer bailout is safe only when the compiler can prove that the original runtime candidate remains intact.
- Proposed change: fail config and configured-component resolution with a file/module-specific diagnostic. Reserve a typed `LoweringDecline` result for expected unsupported lowerings; let unexpected exceptions escape with their original stack and source span. Do not use `proxyWorm` for configured project inputs unless the caller explicitly opts into a documented best-effort mode.
- Risk / what could make this wrong: some third-party modules intentionally fail during static evaluation while their exports are irrelevant. That is a valid reason for an explicit ignore list or opt-in best-effort evaluator, not a process-wide catch that defaults to continuation and hides the offending module.

### F5. Metro drops source locations from compiler diagnostics [medium] [medium] [READ]

- Evidence: compiler diagnostics carry `span` and `component` in `code/compiler/compiler-core/src/diagnostics.ts:31-48`. Metro maps each plan diagnostic to a `MetroCompilerDiagnostic` using only `code`, `message`, and `dependencyId` at `code/compiler/metro-plugin/src/frontend.ts:759-771`; `MetroCompilerDiagnostic` has no source span or line field (`code/compiler/metro-plugin/src/diagnostics.ts:9-21`). The user-facing reporter prints only code and message at `code/compiler/metro-plugin/src/index.ts:136-139` and `code/compiler/metro-plugin/src/transformer.ts:120-127`.
- The lower-level parser has the same quality gap for thrown parse errors: `code/compiler/compiler-core/src/yuku.ts:180-186` includes the module path but concatenates parser messages without line/column or a remediation.
- Why it matters: a Metro user sees “transform-failed: Style prop X could not be safely extracted” without the source location needed to find the prop, and without the action the zero-runtime diagnostics already model. The compiler had the span before the adapter discarded it.
- Proposed change: preserve `SourceSpan` through Metro's diagnostic type and format `relative-file:line:column` at the reporting boundary. Give fallback/unsupported messages a remediation when one is known, such as “keep this value on the runtime path,” “use a static value,” or “move the module to a full-runtime island.” Use the same formatter for parser errors so every compiler-originated diagnostic has one shape.
- Risk / what could make this wrong: Metro may not have source text for every cached diagnostic at report time. The cached module record already has the module id and source hash, and a location can still be formatted from the stored span without requiring a new parse.

## Ideas

- `code/compiler/analyzer-spike` is not abandoned. Its README describes it as a private, reviewable E2 experiment, and its package scripts plus correctness harness are still present. Treat it as an intentional experiment until the E2 decision lands, not dead production code.
- `TAMAGUI_OPTIMIZE_THEMES` is written by Vite and Next but has no source reader. This is already called out as a dead flag in `plans/v3-zero-runtime-mode.md:169`; remove it as a separate cleanup when that planned inventory is acted on rather than reopening it as a new compiler gap.
- The TypeScript language service and ESLint rule are aligned with the compiler grammar: `code/core/language-service/src/core.ts:1-10,168-175` and `code/core/eslint-plugin/src/validFlatValues.ts:1-55` both consume `@tamagui/style-grammar/tooling` and the serialized compiler config. The duplicate grammar finding is specific to the Rust LSP.
