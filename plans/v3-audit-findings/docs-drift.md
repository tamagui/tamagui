# docs drift and public API surface

## Summary

- The highest-risk current docs still teach v2 theme vocabulary. `intro/themes.mdx`, `core/configuration.mdx`, and `core/theme.mdx` use camelCase keys such as `backgroundHover`, while v3 config types contain only kebab-case keys such as `background-hover`. Several current examples also use removed v5 palette names such as `blue10` and `gray10`.
- The docs site does not document two shipped v3 headline surfaces: the root `html.*` runtime frontend and the ordinary compiled, compiled-global-CSS, and strict zero-runtime compiler tiers. The only zero-runtime user material is the new starter README; the tier contract is in `plans/`.
- “Stack” is absent from the v3 `@tamagui/core` source barrel. Current docs use it as a component in runnable code blocks and as the inherited base in v3 API text. A direct TypeScript probe reports `TS2305: ... has no exported member 'Stack'`.
- The draft migration guide is stale in a dangerous way. It says `exitStyle` remains valid on web and that `enterStyle` can be converted, but v3 has no implementation of either prop. The real spelling is a flat `enter:` or `exit:` clause.
- A documented final Button example passes a second `{ shift }` argument to `getSize` and `getSpace`. The v3 functions accept one argument, and a cold `tsc` probe reports `TS2554` for both calls.
- The v3 component pages have two documented prop names with no source occurrence: `Checkbox.Indicator disablePassStyles` and `Checkbox/RadioGroup scaleSize`.

## Findings

### F1. Current theme docs teach v2 camelCase keys and removed palette tokens  [severity: high] [size: L] [label: READ]

- Evidence: `code/tamagui.dev/data/docs/intro/themes.mdx:153-210,342-387` teaches `backgroundHover`, `backgroundPress`, `backgroundFocus`, `colorHover`, `colorPress`, `borderColorHover`, `placeholderColor`, `shadowColor`, and `tokens.color.gray10` in unqualified v3 theme examples. `code/tamagui.dev/data/docs/core/configuration.mdx:545-560` repeats camelCase keys. `code/tamagui.dev/data/docs/core/theme.mdx:139-141` lists the same names. `code/tamagui.dev/data/docs/core/styled.mdx:120`, `code/tamagui.dev/data/docs/core/animations.mdx:252`, `code/tamagui.dev/data/docs/intro/styles.mdx:124,179,182`, `code/tamagui.dev/data/docs/components/lucide-icons/3.0.0.mdx:46`, and `code/tamagui.dev/data/docs/components/toast/3.0.0.mdx:350-354` use old palette spellings such as `blue10`, `blue5`, `blue11`, or `blue12` as ordinary v3 examples.
- Evidence: v3 source declares only kebab-case semantic keys in `code/core/themes/src/generated.ts:14-30`, including `'background-hover'`, `'border-color-hover'`, `'color-hover'`, `'placeholder-color'`, and `'shadow-color'`. The v6 token declarations at `code/core/config/types/v6.d.ts:22-32,225` contain Tailwind names such as `'gray-50'` through `'gray-950'` and `'blue-500'`; the old `blue10` and `gray10` names occur only in the retained v5 compatibility generated files (`code/core/themes/src/generated-v5.ts`).
- Evidence: `code/tamagui.dev/data/docs/core/tokens.mdx:23-40` also teaches `getTokens({ prefixed: false })` and `getTokens({ prefixed: true })` as the way to select `$`-prefixed values. The v3 implementation is `getTokens(): TokensParsed` with no options in `code/core/web/src/config.ts:123-130`. This is a second, directly copyable sigil-era API mismatch, separate from the style-value examples.
- Why it matters: these are not cosmetic spelling differences. The v3 resolver does not guess camelCase aliases, and a v6 config does not define old palette-step names. A reader copying these examples can get a silently missing theme value or a dropped color.
- Proposed change: rewrite all current/default v3 examples to kebab-case semantic keys and v6 token names such as `blue-500`, `gray-500`, or adaptive `colorN`. Keep old spellings only inside clearly labelled v2 migration input or frozen v5 compatibility sections.
- Risk / what could make this wrong: a page explicitly scoped to a v5 compatibility config may retain v5 keys. The cited pages present these as general v3/default examples, and the current `core/theme.mdx` itself says it is v3 inline-values documentation.

### F2. v3 docs use `Stack`, which is not a v3 component export  [severity: high] [size: M] [label: READ]

- Evidence: `code/tamagui.dev/data/docs/core/styled.mdx:135-164` renders `<Stack>` in two code blocks without an import. `code/tamagui.dev/data/docs/core/tokens.mdx:94` tells readers to use a component “like `Stack`”, and `:147-151` renders `<Stack>`. Current v3 API prose also says Stack in `code/tamagui.dev/data/docs/components/radio-group/3.0.0.mdx:260`, `components/slider/3.0.0.mdx:221`, `components/separator/3.0.0.mdx:53`, `components/tabs/3.0.0.mdx:200`, and `components/toast/3.0.0.mdx:199,226,268,272`.
- Evidence: `code/core/web/src/index.ts:109-118` exports `html`, `Theme`, and `View`, but no `Stack`; `code/core/core/src/index.tsx:69-72` explicitly overwrites and exports `View` and `Text`. `code/ui/stacks/src/Stacks.tsx:27-58` exports only `YStack`, `XStack`, and `ZStack`. A direct probe importing `Stack` from the core source barrel was run with TypeScript and failed: `TS2305: Module ... has no exported member 'Stack'`.
- Why it matters: a user following the runnable examples cannot compile them, and the prose perpetuates the old base-component name even though v3's compatibility contract is “use `View`”.
- Proposed change: replace component references and code blocks with `View`; retain `XStack`, `YStack`, and `ZStack` only when describing those actual styled layout components. Update inherited-prop prose to say “View props” or the relevant concrete component.
- Risk / what could make this wrong: `Stack` still appears in internal type names such as `StackStyleBase`, and v2 compatibility material may mention it. The finding is limited to user-facing current docs and a value-level component named `Stack`.

### F3. Root `html.*` and the compiler tier ladder are shipped but undiscoverable in the docs site  [severity: high] [size: L] [label: READ]

- Evidence: `code/core/web/src/index.ts:109-118` exports `html` from the regular web barrel. `code/core/web/src/dom/html.tsx:929-970` constructs the full `html` namespace. `code/ui/tamagui/src/index.ts:279-281` explicitly calls it “the recommended DOM frontend”; `code/core/web/src/dom/standalone.ts:28-31,38-41,48-51,66-69,95-98` marks the standalone DOM surface as deprecated and directs new code to `html` from `tamagui` or `@tamagui/core`.
- Evidence: a scoped search over `code/tamagui.dev/data/docs/**/*.mdx`, all README files, `README.md`, `code/starters`, and `code/demos` found no user-facing `import { html } from 'tamagui'`, `html.div`, `html.section`, or `@tamagui/dom` guidance. The only HTML page is the older `code/tamagui.dev/data/docs/components/html-elements/2.0.0.mdx:9-25`, which documents named `Section`, `Article`, `Main`, and similar wrappers from `@tamagui/elements`, not the v3 `html.*` namespace. The plan's own search receipt in `plans/v3-zero-runtime-mode.md:700-726` records that regular `html.*` should be the public frontend and standalone DOM should not be documented.
- Evidence: the same user-facing search found no `styleMode`, while the only code references are the two test comments at `code/core/tailwind/src/__tests__/frontend.web.test.tsx:18` and `utilities.web.test.tsx:8` saying it is gone. The docs mention the separate Tailwind frontend in `code/tamagui.dev/data/docs/core/config-v6.mdx:74-76` and `guides/how-to-upgrade.mdx:931`, but do not explain the replacement rule that component package provenance selects the frontend. This keeps the lead's correction distinct from an undocumented `styleMode` finding.
- Evidence: `plans/v3-zero-runtime-mode.md:613-625` defines three product tiers: ordinary compiled Tamagui, compiled global CSS, and strict zero-runtime. It also states at `:704-712` that zero-runtime documentation should describe the build mode. Current docs contain no `zero-runtime`, `compiled global CSS`, or strict tier page. `code/starters/zero-runtime/README.md:1-19,27-39` is the only user-facing material found, and it is a starter-specific contract and measurement README.
- Why it matters: the recommended semantic HTML API, the native runtime mapping, and the largest v3 bundle/performance choice are absent from the product's discovery path. Users see a legacy named-wrapper page and cannot learn which frontend or build tier to choose.
- Proposed change: add a v3 DOM/frontend page centered on `import { html } from 'tamagui'`, with web/native examples and a short warning that `tamagui/dom` and `@tamagui/core/dom` are compiler-only compatibility plumbing. Add a compiler modes page linking ordinary compilation, `outputCSS`/compiled global CSS, and strict zero-runtime, with the authoring restrictions and integration status.
- Risk / what could make this wrong: the zero-runtime fixture is still experimental in the plan, so the page must label its support status and avoid promising all integrations beyond the qualified ones. The absence of docs and the root export are independently verified.

### F4. The draft migration guide gives the wrong `enterStyle`/`exitStyle` story and omits the Variables removal  [severity: high] [size: M] [label: READ]

- Evidence: `plans/v3-breaking-change-codemod-guide-draft.md:211-216` says “Legacy `exitStyle` works on web through the animation driver”, says flat `exit:` is rejected on web, and says the codemod keeps `exitStyle` in shared/web files. The same draft's example at `:331-343` converts `enterStyle` while leaving `exitStyle` authored.
- Evidence: a source search over `code/core/web/src`, `code/core/core/src`, and `code/ui` found no implementation or public prop declaration for `enterStyle` or `exitStyle`. The only occurrences are migration/codemod fixtures and comments, for example `code/core/codemod-flat-values/src/legacyConditions.ts:15-16`. The v3 grammar is documented and implemented as flat clauses in `code/tamagui.dev/data/docs/guides/flat-values.mdx:29-37`, and the handoff record at `plans/v3-handoff-log.md:2767-2791` explicitly retracts the earlier probe because these are V2 names.
- Evidence: the codemod does cover the conversion names, but contradicts the draft's keep-on-web instruction. `code/core/codemod-flat-values/src/legacyConditions.ts:8-16` maps both `enterStyle` and `exitStyle` to `enter` and `exit`, and `code/core/codemod-flat-values/src/convert.ts:991-1001,1215-1240` emits those contributions as flat programs. A search over `code/core/codemod-flat-values/src` found no `<Variables>` conversion path, so the codemod does not cover that separate API removal.
- Evidence: the draft has no `<Variables>` migration section. V3's actual implementation has only inline theme-key props on `Theme`, documented by `code/core/web/src/views/Theme.tsx:35-52,58-76`; no `Variables` component is exported by the source barrels. `plans/v3-handoff-log.md:1905-1919` records that `<Variables>` was removed outright and `<Theme>` inline values are the whole API.
- Why it matters: following the draft leaves dead V2 props in an app and can cause a false belief that web exit lifecycle support is preserved. It also misses a complete component/API removal that changes how custom values are authored.
- Proposed change: archive or rewrite the draft before linking it. State that `enterStyle` and `exitStyle` do not exist in v3 and migrate both to flat clauses where the target supports them. Add the `<Variables>` to inline `<Theme>` migration and explain that config `variables` is a different feature.
- Risk / what could make this wrong: `legacyConditions.ts` intentionally retains old names as codemod input. That tooling occurrence does not make the runtime props public; the source implementation search and TypeScript/API barrel agree that they are absent.

### F5. The final Button guide and token docs call removed `get-token` options  [severity: high] [size: S] [label: READ]

- Evidence: `code/tamagui.dev/data/docs/guides/how-to-build-a-button.mdx:53-64,84-91,118-122` presents a “final” copy-paste example that calls `getSpace(name, { shift: -1 })` and `getSize(size, { shift: -2 })`. `code/tamagui.dev/data/docs/core/tokens.mdx:65-76` and `code/tamagui.dev/data/docs/guides/how-to-upgrade.mdx:601-620` correctly say the options argument was removed, but the Button guide was not updated.
- Evidence: `code/core/get-token/src/index.ts:11-27` defines `getSize`, `getSpace`, and `getRadius` with exactly one argument. A cold `bunx tsc --noEmit` probe against the source module reported `TS2554: Expected 1 arguments, but got 2` for both `getSize('md', { shift: -2 })` and `getSpace('md', { shift: -1 })`.
- Why it matters: this is a prominent copy-paste guide whose “ready to copy” code does not typecheck on v3.
- Proposed change: use `getVariableValue(getSpace(name))` or explicit token keys and numeric multiplication, matching the upgrade guide. Add a typecheckable CI extraction check for this guide if code blocks are intended to remain executable.
- Risk / what could make this wrong: a future compatibility overload could restore the options signature, but that would contradict the current source and the explicit v3 migration documentation.

### F6. v3 component pages document absent props  [severity: medium] [size: S] [label: READ]

- Evidence: `code/tamagui.dev/data/docs/components/checkbox/3.0.0.mdx:240-244` documents `Checkbox scaleSize`; `:280-284` documents `Checkbox.Indicator disablePassStyles`; `code/tamagui.dev/data/docs/components/radio-group/3.0.0.mdx:356-360` documents `RadioGroup.Item scaleSize`.
- Evidence: scoped searches of `code/ui/checkbox/src`, `code/ui/radio-group/src`, `code/core`, and `code/ui` found no `scaleSize` or `disablePassStyles` declaration or use. The actual Checkbox prop types at `code/ui/checkbox/src/Checkbox.tsx:85-100` contain `forceMount`, `activeStyle`, and `activeTheme`, but neither documented name. The actual RadioGroup item type at `code/ui/radio-group/src/RadioGroup.tsx:68-73` contains `value`, `id`, `labelledBy`, and `disabled`, but not `scaleSize`.
- Why it matters: these pages promise props that have no v3 source path, so users cannot implement the documented sizing or style-pass behavior.
- Proposed change: remove the rows or replace them with the actual v3 sizing/styling API, then generate the tables from public types where practical.
- Risk / what could make this wrong: a prop could be supplied by an external wrapper outside `code/core` and `code/ui`; no such wrapper is used by the current component source, and the exact source packages named by each page were searched.

### F7. The public barrels have a recommended export with no documentation, while the docs still foreground a legacy wrapper API  [severity: medium] [size: M] [label: INFERRED]

- Evidence: `@tamagui/core` re-exports the regular DOM frontend through `code/core/web/src/index.ts:109` and `tamagui` exposes it explicitly at `code/ui/tamagui/src/index.ts:279-281`. The docs search found no `html.*` API example, while `code/tamagui.dev/data/docs/components/html-elements/2.0.0.mdx:9-25` presents `@tamagui/elements` named wrappers as the HTML story.
- Evidence: the same `tamagui` barrel explicitly exposes lower-level sizing helpers `createSizeContext`, `createSizeTable`, `defaultTokenSizePolicy`, `resolveSizeToken`, and `resolveTokenSize` at `code/ui/tamagui/src/index.ts:260-267,301-304`. `resolveTokenSize` is only mentioned incidentally in the migration table at `code/tamagui.dev/data/docs/guides/how-to-upgrade.mdx:117`; `createSizeContext` and `createSizeTable` have no docs matches. These may be deliberate lower-level exports, but the barrel currently gives no public/experimental classification.
- Why it matters: users cannot tell which root exports are supported product API and which are implementation plumbing. The HTML case is especially confusing because the old named wrappers and new `html.*` frontend coexist.
- Proposed change: document `html.*` as the supported public frontend and mark low-level size helpers as either supported with a reference page or internal/unstable. Keep the API source of truth in the root barrel and avoid sending users to a deep import merely to discover a root export.
- Risk / what could make this wrong: some size helpers may intentionally be public for component authors rather than app authors. The finding is about missing classification and documentation, not a demand to remove them.

### F8. The migration story exists as a real user page, but the draft is not the source of truth and misses additional proven breaks  [severity: medium] [size: M] [label: INFERRED]

- Evidence: `code/tamagui.dev/data/docs/guides/how-to-upgrade.mdx:1-9` is a real v2-to-v3 user-facing guide, so the migration story is not absent. It covers package/config changes, flat values, Sheet anatomy, removed props, token stepping, FocusScope, Select, icons, Toast, and defaultProps in later sections.
- Evidence: the draft's manual migration list at `plans/v3-breaking-change-codemod-guide-draft.md:34-48` does not mention the documented-but-absent `Checkbox/RadioGroup scaleSize` or `disablePassStyles` names, the `<Variables>` removal, or the standalone DOM demotion to regular `html.*`. It also contains the contradictory `enterStyle`/`exitStyle` section cited in F4. The source JSDoc at `code/core/web/src/dom/standalone.ts:28-31,38-41,48-51,66-69,95-98` gives the replacement direction explicitly.
- Why it matters: the repo contains two migration narratives with different validity. A maintainer or beta user following the draft can undo the corrected v3 API decisions even though the current page has a real migration flow.
- Proposed change: make the published `how-to-upgrade` guide the single maintained migration source, either delete the draft or mark it historical and link the published guide. Add a source-verified checklist for removed props and the Theme inline-values migration.
- Risk / what could make this wrong: the draft is internal and may be intentionally historical. It is still a launch risk if it is discoverable or used by agents because it gives behaviorally wrong instructions.

## Ideas (speculative, not findings)

### I1. Generate prop tables from the public declaration surface

The absent `scaleSize` and `disablePassStyles` rows, plus repeated inherited `Stack` prose, suggest a docs build check could resolve component prop tables against generated `.d.ts` files. This is an idea only because the docs table format also includes explanatory and migration-only rows that need human curation.

### I2. Add a docs code-block typecheck lane

The `get-token` failure was caught by a six-line probe. A docs test could extract only blocks marked as copy-pasteable and typecheck them against the package source, while leaving intentionally illustrative migration input uncompiled.
