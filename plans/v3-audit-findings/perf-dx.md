# runtime performance and developer experience

## Summary

- **F1 [high]** Media changes broadcast to every subscribed component. Each callback then scans that component's touched keys, so a single breakpoint change is O(number of media subscribers), even when most subscribers use unrelated keys.
- **F2 [high]** Theme provider bookkeeping leaves `themeProviderParents` entries behind on the normal provider cleanup path. Dynamic or frequently mounted themes can retain provider IDs and parent IDs for the life of the process.
- **F3 [high]** Several lifetime caches have no bound or invalidation: theme names, generated CSS variables, and native compiled style mappings. Existing variable and inline-theme caches are bounded, so this is a separate set of gaps.
- **F4 [medium]** The web provider calls `config.getCSS()` during render, and the full CSS path regenerates theme rule sets and serializes all auto variables. This makes SSR and first paint pay for work that is mostly configuration-static.
- **F5 [known-open]** The retained native runtime benchmark shows a V3 runtime gap in simple, themed, rich, and group scenarios, but the current evidence does not attribute the cost to individual native hooks or the `html.*` path. A native-specific mount/update profile is still missing.
- **F6 [known-open]** No end-to-end cold/warm compiler-speed harness exists. The analyzer spike has useful synthetic timings, but it does not measure the public plugin through a bundler and cannot answer what a user's build feels like.
- **F7 [high]** Clause-bearing style values deliberately fall back to `(string & {})`. Users get a prefix completion but no type checking or completion for payloads such as `opacity="1 enter:0 exit:0"`.
- **F8 [medium]** Runtime debug tooling can show resolved props, themes, and token provenance, while compiler bailout records already contain a code, message, span, and component. There is no per-element developer view that explains whether a style was compiled, lowered, runtime-resolved, or dropped.
- **F9 [medium]** Several warnings and production errors are too opaque to act on. The ten worst strings are ranked below with their exact source locations.

This report is source-based except where it cites the retained benchmark and analyzer measurements. I did not run a fresh render-count or build-time benchmark in this audit worktree.

## Findings

### F1 Media and context fan-out [high] [M] [READ / INFERRED]

- Evidence: `code/core/web/src/createComponent.tsx:361-362` reads `ComponentContext`, `:496` reads `GroupContext`, `:814-827` calls `useThemeWithState` and `useMedia` for every component, and `code/core/web/src/hooks/useThemeState.ts:103-105` reads `ThemeStateContext` inside the theme hook. A component with a styled context adds another `useContext` at `createComponent.tsx:353-358`. On native Android, `NativeMenuContext` is another conditional read at `:364-375`.
- Evidence: `code/core/web/src/hooks/useMedia.tsx:92-96` stores every media subscriber in one Set and calls every callback from `updateMediaListeners`. Each callback then loops only its own touched keys at `:257-284`. The subscription callback can still force a React update at `:342-356`.
- Evidence: a theme update is more selective. `code/core/web/src/hooks/useThemeState.ts:586-607` walks the descendant listener graph and invokes subscribed descendants. A forced config update instead loops all registered listeners at `:36-40`. Group and media-group changes use a per-group subscription path from `code/core/web/src/createComponent.tsx:1610-1617`.
- Why it matters: a normal leaf has at least three context reads plus theme and media subscription machinery. A media change with one changed key still invokes every media subscriber, including `_withStableStyle` wrappers. `code/core/web/src/_withStableStyle.tsx:22-28` calls `useMedia()` without a component UID, so it takes the global subscription path. A hover or press state normally updates the owning component's `useState` at `code/core/web/src/hooks/useComponentState.ts:188-215`; group pseudo-state can fan out to all members of that group. The source establishes the fan-out shape, but a fixture is needed to give exact render counts for a particular tree.
- Proposed change: index subscriptions by touched media key and publish only to buckets for keys whose boolean value changed. Keep a separate bucket for subscribers that intentionally observe the full media object. Add a small render-count fixture covering one theme, one media key, one group state, and one hover event. Record callback count and committed render count separately because the native fast path can commit without React at `useMedia.tsx:351-355` and `useThemeState.ts:215-223`.
- Risk / what could make this wrong: the existing global broadcast may be intentional for media configuration changes that replace the complete query map. The keyed index must handle HMR and `configureMedia` replacing keys without leaving stale buckets. The render-count claims above are structural until the fixture runs.

### F2 Theme provider registry leak [high] [S] [READ]

- Evidence: `code/core/web/src/hooks/useThemeState.ts:135-144` writes every cascading provider ID into `themeProviderParents` and writes or deletes its inline layer. The normal subscription cleanup at `:235-243` deletes listeners, `localStates`, `states`, and pending updates, but it does not delete `themeProviderParents` or `inlineThemeLayers`. `cleanupThemeState` at `:315-324` deletes those two maps only when `r.unsubscribe` is already absent, which is the opposite of the ordinary subscribed-provider path.
- Why it matters: each mounted provider normally gets a distinct `useId` at `:127-130`. A provider that mounts and unmounts repeatedly can leave its ID and parent ID reachable from a process-wide Map. The retained value includes the parent ID, and inline layers can include the value object. This is memory growth with app lifetime, independent of the bounded style caches.
- Proposed change: make the provider cleanup path delete `themeProviderParents` and `inlineThemeLayers` for the provider ID after unsubscribing. Add a lifecycle probe that mounts and unmounts a dynamic `<Theme>` repeatedly, then checks the registry size through a development-only inspection hook or an internal test seam.
- Risk / what could make this wrong: portal bridging may read a provider entry after React cleanup during a short transition. Cleanup must happen after the last render that can be observed by the bridge, and the probe should exercise portals and Strict Mode. The asymmetry between the two cleanup branches is directly visible, while the retained heap size needs runtime confirmation.

### F3 Unbounded dynamic-value caches [high] [M] [READ / INFERRED]

- Evidence: `code/core/web/src/hooks/useThemeState.ts:69-73` creates `themeNameCache` as a process-wide Map. It clears only when `cacheVersion` changes at `:635-638`, then inserts every distinct cache key at `:643-650`. No size limit exists. The same file documents `states` and `localStates` as Maps that “will gain memory over time” at `:31-33`, although the listener cleanup does remove their normal component entries at `:235-240`.
- Evidence: `code/core/web/src/helpers/registerCSSVariable.ts:40-56` stores every distinct token or literal value in `tokensValueToVariable` and `autoVariables`. Runtime-mutated values take a second unbounded Map and array at `:59-75`. `code/core/web/src/helpers/createDesignSystem.ts:194-197` serializes all `autoVariables` into CSS whenever the full CSS path runs.
- Evidence: the native engine stores each mapping key in `compiledMappings` at `code/core/web/src/helpers/nativeStyleEngine.ts:69-90`, and each distinct state name in `compiled.states` at `:94-109`. The only shown invalidation is clearing all compiled mappings when the engine identity changes at `:112-115`; there is no per-config or size bound.
- Why it matters: theme builders, live previews, tenant-specific values, and generated state names can produce unbounded distinct keys during one long-lived app process. A cache hit is useful for repeated values, while a cache with no eviction turns user input cardinality into retained memory. The existing `rulesCache`, `flatLayers`, and `mergedThemeCache` explicitly clear at 10,000 entries in `code/core/web/src/helpers/variables.ts:313`, `:419-424`, `:612`, `:669-673`, and `:677`, `:835-840`, so the missing bounds here are concrete rather than a general cache complaint.
- Proposed change: define ownership and lifetime for each cache. Clear theme-name entries when the associated config/theme registry changes, and bound dynamic CSS-variable and native state caches with the same documented limit used by the existing variable caches. Prefer an explicit cache reset when a theme-builder session is replaced, because evicting a variable that is still referenced by emitted CSS could break that session.
- Risk / what could make this wrong: CSS variables and native mappings can outlive the component that first requested them, so blind LRU eviction could invalidate live output. A correct fix needs a generation or session boundary, or reference-aware retention. The growth risk is READ from the map/array ownership; the exact production growth rate is INFERRED until a long-running dynamic-value probe measures it.

### F4 Full CSS regeneration during provider render [medium] [M] [READ / INFERRED]

- Evidence: `code/core/web/src/views/TamaguiProvider.tsx:86-98` embeds `config.getCSS()` in the render output of every web provider render. The full path in `code/core/web/src/helpers/createDesignSystem.ts:184-197` calls `getAllRules().join`, calls `themeConfig.getThemeRulesSets().join`, and maps every auto-generated variable. The design-system string is rebuilt at `:211-227`. `createTamagui.ts:202-223` defines `getThemeRulesSets()` as a fresh `createThemeCSS(dedupedThemes, configIn)` call.
- Why it matters: SSR and the first client render repeatedly pay for joining runtime rules, rebuilding theme rule sets, mapping variable arrays, and constructing large strings. Those operations are configuration-static for a given config and CSS options, while the runtime rule list is the part that changes as components are discovered. This is a mount and request cost, separate from steady-state style resolution.
- Proposed change: precompute the static design-system, theme rule sets, and initial auto-variable CSS when `createTamagui` constructs the config. Make `getCSS()` append only newly accumulated runtime rules, preserving `sinceLastCall` semantics and explicit `exclude` options. Add an SSR benchmark with 1, 10, and 100 requests using the same config, measuring `getCSS()` time and output equality.
- Risk / what could make this wrong: runtime theme-builder updates and late CSS-variable registration must invalidate the static fragment. The cache key needs to include the CSS separator and exclusion mode, and the implementation must keep server isolation when multiple configs exist in one process. The recommendation applies to the static fragment only; it does not reuse stale runtime rules.

### F5 Native runtime hot paths lack attribution [known-open] [M] [READ / INFERRED]

- Evidence: the retained measurement in `code/comparisons/V3_BETA_MEASUREMENT_STATE.md:103-109` reports native runtime simple mount at V3 27.49 ms versus V2 23.98 ms, with a paired confidence interval of +2.36 to +4.65 ms. The retained table at `code/comparisons/output/benchmarks-native-v2-v3.md:18-29` shows the same runtime gap for simple, themed, rich, and group mounts or updates, with the stated caveat that compiled V3 cells are invalid at `:5-14`. This finding uses the valid runtime comparisons only.
- Evidence: the native component path still reads `ComponentContext` and `GroupContext` at `code/core/web/src/createComponent.tsx:361-375` and `:496`, calls `useThemeWithState` and `useMedia` at `:814-827`, then installs group/media subscriptions at `:1596-1629`. The theme and media hooks can use native fast-path callbacks, but their setup and snapshot work remains in the mount path. The exact contribution of each hook and of `html.*` prop normalization is unmeasured.
- Why it matters: Hermes and native view updates have different costs from web CSS generation. A web chunk or allocation win does not identify the native bottleneck. The valid benchmark shows a native runtime gap, while the source points to several candidate layers with no attribution.
- Proposed change: add a native-only profiler fixture for simple, themed, media-dependent, group-dependent, animated, and `html.*` components. Split mount into hook setup, style-plan lookup, theme snapshot, media snapshot, prop mapping, and native commit. Run it in a quiet Release simulator and on one physical device before changing the fast path.
- Risk / what could make this wrong: the retained benchmark is load-caveated and reports direction more strongly than absolute values. The source evidence does not prove which layer causes the gap, so any optimization before the profile would be speculative.

### F6 Compiler build-time performance is still unmeasured end to end [known-open] [M] [READ]

- Evidence: `code/comparisons/V3_BLOG_NUMBERS_GAP_AUDIT.md:100-107` states that no harness records cold and warm compiler wall-clock time across the shared corpus, and that the gap blocks compiler-speed claims.
- Evidence: the analyzer spike reports synthetic graph timings, but its measurements cover an analyzer experiment rather than the public compiler plugin through a bundler. The retained audit therefore cannot answer cold startup, warm no-op rebuild, one-file invalidation, filesystem access, or emitted-code costs for Vite, Metro, or Next.
- Why it matters: compiler time is paid before a developer sees the app, and cache behavior changes the answer dramatically. A small analyzer benchmark cannot identify whether users wait on parsing, module loading, lowering, cache misses, or bundler integration.
- Proposed change: build one retained harness around the supported Vite and Metro plugin entry points. Record cold process, cold filesystem, warm no-op, one-file change, and multi-file change. Attribute transform, analyzer, plan lookup, emit, and bundler overhead separately, with fixed corpus and machine metadata.
- Risk / what could make this wrong: the analyzer spike may already identify the eventual bottleneck, but its synthetic graph is insufficient evidence for an end-to-end claim. Keep its numbers as a lower-level control rather than presenting them as user build times.

### F7 Clause grammar has an open string escape [high] [M] [READ / INFERRED]

- Evidence: `code/core/web/src/types.tsx:2033-2038` documents clause-bearing strings and explicitly says candidate and modifier validation belongs to the compiler and language service. `FlatClausePrefix` only covers the first modifier prefix at `:2040-2055`, while `FlatStyleValue<T>` includes `(string & {})`. `WithThemeValues` propagates that open escape to style props at `:2057-2065`.
- Why it matters: a value such as `opacity="1 enter:0 exit:0"` receives no type validation for the base value, modifier names, payloads, ordering, or repeated clauses. The type system can offer a prefix such as `enter:` but cannot tell the user that `enetr:` is wrong or that a payload is invalid. This is a direct editor-quality gap even though the open escape is a deliberate type-performance choice.
- Proposed change: keep the current open string path for full multi-clause values, and add an opt-in language-service completion and diagnostic layer that parses the existing grammar metadata. For types alone, provide finite per-property token and one-modifier unions only where measured budgets permit. The feasibility plan's measured single-token and one-modifier shape is the right boundary; a full recursive union would make tsserver work and completion worse.
- Risk / what could make this wrong: a large literal union can cause TypeScript instantiation and completion regressions. The fix needs editor measurements and should avoid replacing the current escape globally. It also requires diagnostics to share the compiler's grammar source so type and runtime rules do not drift.

### F8 Compiler decisions are hard to inspect at runtime [medium] [M] [READ / INFERRED]

- Evidence: runtime dev tooling logs props, static config, style state, theme, and rules when `debug="verbose"` at `code/core/web/src/helpers/getSplitStyles.tsx:454-468`. Token provenance can be attached to the winning style object at `:1260-1274`, with the side channel defined in `code/core/web/src/helpers/styleProvenance.ts:1-16`.
- Evidence: the compiler already returns a bailout code, message, source span, and component from `code/compiler/static/src/compilerHost.ts:2962-2983`. Example receipts identify `local/dynamic-style-value` and the style property at `:1819-1825`, or `local/unsupported-target` at `:2084-2102`.
- Why it matters: a user seeing a missing style has to infer whether a compiler bailout, runtime tier, CSS class, native plan, or prop filtering caused it. Token provenance answers which token won, but it does not answer which execution tier handled the style or why a candidate was declined. Compiler evidence already contains most of the explanation needed for a development receipt.
- Proposed change: expose a development-only per-element receipt through the existing debug visualizer or a devtools inspection API. Include component name, style property, tier (`compiled`, `lowered`, `runtime`, or `dropped`), compiler bailout code and message when present, and the final token provenance. Keep it out of production output and avoid adding enumerable host props.
- Risk / what could make this wrong: a full receipt on every host could add memory and render cost. Make collection opt-in through the existing debug setting or an environment flag, and attach it through the existing non-enumerable inspection channel.

### F9 Worst ten user-facing warnings and errors [medium] [S] [READ]

These are ranked by how little context and recovery guidance they provide. The ranking is based on the literal emitted message, not on how often the branch runs.

1. `code/core/web/src/views/Theme.tsx:214`: `throw new Error("‼️010")`. It gives only an internal code. It omits the theme name, provider relationship, component, and recovery step.
2. `code/core/web/src/config.ts:102-105`: production emits `Err0` for a missing config. Development has a useful explanation, but production users and crash reports lose the duplicate-config/setup diagnosis.
3. `code/core/web/src/hooks/useThemeState.ts:626-630`: production emits `❌004` when `name` and `reset` are both passed. Development says what is wrong, while production omits both prop names and the valid alternatives.
4. `code/core/web/src/hooks/useMedia.tsx:69-73`: `throw new Error('⚠️ No match')` does not include the media key, query string, platform, or setup action. It cannot distinguish a malformed query from a missing implementation.
5. `code/core/web/src/helpers/insertStyleRule.tsx:378-387`: production logs `Error inserting style rule` plus the rules array. It omits the identifier, selector, stylesheet target, and whether the caller should remove or fix a declaration.
6. `code/ui/sheet/src/SheetImplementationCustom.tsx:1296-1302`: `Invalid snapPoint percentage string` and `Invalid snapPoint unknown value` omit the received value, the sheet component, and accepted examples.
7. `code/ui/sheet/src/SheetImplementationCustom.tsx:1314-1317`: `Invalid snapPoint percentage` has the same missing value and recovery information for the numeric conversion path.
8. `code/ui/portal/src/GorhomPortalItem.tsx:11-14`: `No hostName` does not name the portal item or say to add `hostName` or set `passThrough`.
9. `code/core/web/src/helpers/matchMedia.native.ts:7-10`: `warning: matchMedia implementation is not provided.` omits the affected media keys and the required `setupMatchMedia` call.
10. `code/core/web/src/hooks/useComponentState.ts:263-265`: `has presenceState ${JSON.stringify(presenceState)}` is a debug warning without component name, lifecycle context, or an action. It can also dump a large object into the console.

- Proposed change: replace internal production error codes with stable codes plus a short context payload, preserving the readable development text. Include component or prop names, received values where safe, and one recovery action. For style insertion failures, include the style identifier and a sanitized rule or selector. Route warnings through a shared formatter so production diagnostics and development diagnostics carry the same fields.
- Risk / what could make this wrong: changing literal messages can affect consumers that snapshot logs, although source-string assertions are poor behavior tests. Keep machine-readable error codes stable while improving the human message, and avoid printing secrets or unbounded serialized props.

## Ideas

- **IDE grammar service [IDEA].** Reuse the compiler's `toolingDiagnostics.ts` grammar metadata in a TypeScript language-service plugin. Offer completion after a modifier prefix and diagnostics for misspelled modifiers and invalid payloads without placing the full grammar in every component prop type.
- **Render fan-out receipt [IDEA].** In the same opt-in debug mode as F8, count theme, media, group, and local-state callbacks per interaction. This would turn “one hover” and “one breakpoint change” into a reproducible profile instead of a source-only estimate.
- **Cache lifetime contract [IDEA].** Document which caches are config-lifetime, app-lifetime, or session-lifetime. Expose development counters for current size and distinct-key rate, then use those counters to choose bounds from observed dynamic-value workloads.
