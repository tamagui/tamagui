# competitive styling systems audit

## Summary

- **READ:** v3 has the broadest condition model in this set: one value can route state, media, group, container, theme, and platform clauses through `directStyle.ts:295-418`. The v2 counterpart for that work is 1,573 gzip bytes larger (`plans/v3-handoff-log.md:1984-1999`).
- **READ:** v3 is the only system here with a measured web zero-runtime tier that removes Tamagui's renderer, style engine, provider, theme state, media state, and component animation machinery from the entry graph (`plans/v3-zero-runtime-mode.md:79-91`; `plans/v3-handoff-log.md:1862-1865`).
- **READ:** Unistyles is the strongest native-runtime competitor. Its public v3 contract combines a mandatory Babel plugin with a C++/Nitro core, Shadow Tree integration, and zero re-renders (`~/github/react-native-unistyles/skills/react-native-unistyles-v3/SKILL.md:15-25`). Closing that gap is a native-engine project, not a small Tamagui optimization.
- **READ:** StyleX is the strongest web-server and authoring-tools competitor. Its runtime `create()` deliberately throws unless the Babel compiler ran (`~/github/stylex/packages/@stylexjs/stylex/src/stylex.js:65-79`), and its repository includes RSC examples, an ESLint suite, and a no-unused rule (`~/github/stylex/packages/@stylexjs/eslint-plugin/README.md:40-47,156-167`).
- **INFERRED:** v3 should market “one grammar, multiple lowering tiers, one web/native component surface” and avoid claiming that its full runtime beats Unistyles or that its regular runtime is RSC-safe. The repo has evidence for the first claim and explicit client-only limits for the second (`plans/v3-zero-runtime-mode.md:899-906`).
- **INFERRED:** The cheapest high-value additions are analysis and diagnostics products built on the existing parsed program, registry, source spans, and lowering receipts. A new native engine, a full RSC component contract, and a universal Tailwind class frontend are materially larger bets.

### F2. What competitors do that v3 does not  [severity: high] [size: L] [label: INFERRED]

The ranking is by the amount of new machinery v3 would need, not by how attractive the feature is.

1. **Unistyles native C++/Nitro and Shadow Tree styling (L).** **READ:** Unistyles requires New Architecture and Nitro, advertises a C++ core and no re-renders, and its source contains a C++ parser, registry, and Shadow Tree manager (`react-native-unistyles/.../SKILL.md:17-25`; `react-native-unistyles/packages/unistyles/cxx/parser/Parser.cpp`; `.../cxx/shadowTree/ShadowTreeManager.cpp`). **What users get:** theme, breakpoint, and runtime updates without React re-rendering and with native-side style application. **What v3 would build:** a supported native module, JSI/Nitro bindings, a native style registry, Shadow Tree commit integration, and a migration/debug story for two rendering engines. **Recommendation:** decline for the first v3 release. v3's compiler and direct JS runtime can make static and dynamic paths cheaper, but they do not turn JS style evaluation into a C++ Shadow Tree engine.

2. **StyleX's explicit RSC/static-CSS contract (L).** **READ:** StyleX's runtime throws if `create()` reaches runtime, its compiler emits CSS, and the repo has a Vite RSC example (`stylex/stylex/src/stylex.js:65-79`; `stylex/babel-plugin/README.md:3-10`; `stylex/examples/example-vite-rsc/README.md`). **What users get:** server components can author styles without importing a client style engine, and the build owns CSS extraction. **What v3 would build:** a server-safe public entry with no hooks, context, or runtime imports; a compiler guarantee for every server-visible component; generated CSS ownership that works with RSC/Flight boundaries; and a documented client boundary for genuinely dynamic state. **Recommendation:** build a small RSC-safe DOM/zero entry first (L), rather than promising that all regular Tamagui components are RSC-compatible.

3. **StyleX's mature static-analysis/tooling package (M).** **READ:** StyleX ships valid-style, valid-shorthand, sort-key, enforce-extension, and no-unused ESLint rules (`stylex/eslint-plugin/README.md:40-167`) plus a devtools extension (`stylex/packages/@stylexjs/devtools-extension/README.md`). **What users get:** invalid style declarations, unused styles, ordering mistakes, and theme-file conventions are caught in the editor. **What v3 would build:** ESLint rules and a devtools protocol consuming the already-existing grammar diagnostics, program hashes, and compiler source spans. **Recommendation:** build this. It is a product layer over existing IR, not a second styling engine.

4. **NativeWind's Tailwind ecosystem and custom-CSS escape hatch (M).** **READ:** NativeWind advertises Tailwind compiler integration, arbitrary classes, CSS variables, custom CSS, group modifiers, container queries, and transitions (`nativewind/README.md:40-59`). **What users get:** existing Tailwind knowledge, utilities, plugins, and CSS files transfer into React Native projects. **What v3 would build:** a stable className frontend with Tailwind plugin/config compatibility, arbitrary-value and custom-CSS handling, generated class typing, and a support matrix for web/native differences. v3 has a separate Tailwind frontend, but the standalone DOM entry deliberately carries neither regular style props nor the Tailwind parser (`code/core/web/src/dom/standalone.ts:7-18`). **Recommendation:** keep the frontend separate and make its parity/entrypoint story explicit. Do not merge Tailwind parsing into regular Tamagui or standalone DOM.

5. **Unistyles' no-new-components and third-party prop bridge (M).** **READ:** Unistyles advertises a clean view hierarchy and provides `withUnistyles` for theme/runtime-derived non-style props (`react-native-unistyles/README.md:40-53`; `.../SKILL.md:104-116`). **What users get:** existing React Native components can consume themed values without adopting Tamagui components. **What v3 would build:** a general wrapper that maps theme/runtime values to arbitrary component props while preserving refs, memoization, and compiler visibility. **Recommendation:** build a narrow, documented adapter for third-party components only if migration demand proves it. Tamagui's own component and `styled()` model is a stronger place for variants and cross-platform semantics.

6. **Unistyles' first-class Next SSR collection API (M).** **READ:** `useServerUnistyles()` and `hydrateServerUnistyles()` are documented for App Router and Pages Router (`react-native-unistyles/.../styling-patterns.md:612-660`). v3 has SSR and streaming tests, but its zero-mode islands are explicitly client-only (`plans/v3-zero-runtime-mode.md:899-906`). **What v3 would build:** a public server collector and hydration API that works with full-runtime components, not only compiler-owned CSS artifacts. **Recommendation:** build it only as part of the RSC-safe entry; the existing compiler artifact path should remain the primary zero-mode API.

7. **NativeWind's familiar className adoption path (S/M).** **READ:** NativeWind's public API is Tailwind `className` and its package uses a Metro wrapper that delegates to `react-native-css` (`nativewind/README.md:20-26`; `nativewind/src/metro.tsx:1-15`). **What users get:** low migration friction for teams already using Tailwind. v3's regular API remains typed Tamagui props and its standalone DOM explicitly excludes `className` in type tests (`code/core/web/src/dom/standalone.test-d.ts:54-60`). **Recommendation:** say this is a deliberate frontend choice, then provide a good `@tamagui/tailwind` migration guide. A universal className surface would create a second precedence and typing system.

### F3. What v3 does better and is not saying  [severity: high] [size: S] [label: READ]

These are claims the repository can currently support. Claims about beating another system's total bundle or frame time are excluded because the retained neutral cross-framework campaign is still deferred (`code/comparisons/V3_BLOG_NUMBERS_GAP_AUDIT.md:68-77`).

1. **Claim:** “Write state, media, group, container, theme, and platform conditions in one value grammar, and v3 routes them through one precedence model.” **Evidence:** the parser is one left-to-right pass (`code/core/style-grammar/src/valueParser.ts:1-22,188-261`), and `directStyle` handles all condition kinds in one pass (`code/core/web/src/helpers/directStyle.ts:295-418`). **Status:** supported.

2. **Claim:** “v3 does more condition routing with 1,573 fewer gzip bytes than v2.” **Evidence:** the retained same-fixture, same-gzip comparison records v3 condition routing at 1,123 gzip bytes versus v2 at 2,696 (`plans/v3-handoff-log.md:1984-1999`). **Status:** supported. The claim must name this group, not imply that the whole v3 bundle is smaller than v2.

3. **Claim:** “The compiler has useful tiers instead of an all-or-nothing extraction switch.” **Evidence:** the lowering plan tracks found, lowered, flattened, styled, and bailed candidates (`code/compiler/compiler-core/src/lower.ts:20-26`); dynamic style props can remain as narrow host properties (`code/compiler/static/src/compilerHost.ts:1319-1333,1412-1419`); successful web output can be class plus inline style (`code/compiler/static/src/compilerHost.ts:2860-2908`). **Status:** supported.

4. **Claim:** “A conforming v3 zero-runtime web entry is close to plain React.” **Evidence:** the zero plan defines the graph as having no Tamagui renderer/style engine/provider/theme/media/animation machinery (`plans/v3-zero-runtime-mode.md:79-87`) and the retained probe measured seven gzip bytes over hand-written React (`plans/v3-zero-runtime-mode.md:89-91`). **Status:** supported for the zero contract and probe shape. Do not generalize it to regular full-runtime Tamagui.

5. **Claim:** “`html.*` gives v3 a native DOM runtime twin, not a web-only tag alias.” **Evidence:** the native runtime maps DOM props, wraps literal text, and reads the same generated tables as the compiler (`code/core/web/src/dom/htmlRuntime.native.tsx:7-24,56-75,193-205`); the backing table names the native primitives and the compiler contract (`code/core/dom/src/tables/nativeBacking.ts:1-21,75-104`; `code/core/dom/src/contract.ts:11-27`). **Status:** supported.

6. **Claim:** “The same semantic `html.*` surface can lower to web tags or native primitives.” **Evidence:** the DOM structural pass validates the same imported `html` elements for both compiler targets (`code/compiler/static/src/domStructuralPass.ts:19-24,30-84`), while native backing is table-driven (`code/core/dom/src/tables/nativeBacking.ts:75-104`). **Status:** supported as a source/component contract. A claim that every DOM tag has identical behavior on both platforms is unsupported because the tables intentionally reject some native tags/props.

7. **Claim:** “v3 has a real SSR and streaming story for conditional styles.” **Evidence:** server rendering is tested for class names and emitted rules (`code/core/core-test/flatValueProgramsSSR.web.test.tsx:112-151`), and streaming tests assert style program blocks are not split across chunks (`code/core/core-test/flatValueProgramsStreaming.web.test.tsx:11-24,54-74`). **Status:** supported for the tested web paths.

8. **Claim:** “The grammar can power editor completion and migration without a second parser.” **Evidence:** source-span parsing and cursor completion share the runtime scanner (`code/core/style-grammar/src/toolingDiagnostics.ts:610-728`), and the codemod imports the shared grammar rather than re-deriving it (`code/core/codemod-flat-values/src/grammar.ts:1-5`). **Status:** supported.

9. **Unsupported claim to avoid:** “v3 is faster than Unistyles because it has zero runtime.” **Evidence:** the repo has a zero-runtime web probe, while Unistyles' advertised native cost is a different native/C++ measurement (`plans/v3-zero-runtime-mode.md:89-91`; `react-native-unistyles/README.md:40-53`). These measurements do not compare the same target or workload.

10. **Unsupported claim to avoid:** “v3 is RSC-safe.” **Evidence:** zero-mode islands are explicitly client-only and server output is a placeholder (`plans/v3-zero-runtime-mode.md:899-906`). The defensible claim is “zero mode has a server/client contract and an RSC-safe subset is a next product.”

### F4. Product implications  [severity: med] [size: M] [label: INFERRED]

- Make the public comparison page a three-axis chart: **authoring grammar**, **lowering tier**, and **runtime host**. This prevents “zero runtime” from being compared with Unistyles' native C++ runtime as though they were the same measurement.
- Lead with the condition grammar and compiler tiers, then show the zero-runtime and native `html.*` receipts. These are the areas where v3 has source-backed differentiation rather than a slogan.
- Say explicitly that `@tamagui/tailwind` is a separate frontend. The standalone DOM entry excludes the Tailwind parser by design (`code/core/web/src/dom/standalone.ts:15-18`), so the product should explain the boundary instead of implying every entry accepts every syntax.
- Publish a capability/support diagnostic for native clauses. `directStyle` already warns when a state has no native source and drops unsupported native values (`code/core/web/src/helpers/directStyle.ts:1712-1729`); exposing that as a documented matrix would turn a limitation into a trust feature.

Every item below is an **IDEA**. Costs are rough implementation sizes for a useful first version, not estimates for a polished product.

### I1. Clause-aware design-system linter [IDEA, M]

Use `parseValueWithSourceSpans`, the modifier registry, candidate target resolver, and `toolingDiagnostics` to flag unknown modifiers, property/candidate mismatches, unsupported native clauses, and values that are valid CSS but not valid for the chosen property. The first version can be an ESLint rule plus editor diagnostics. This is cheap because the parser and diagnostics already exist; it should not invent a second scanner.

### I2. Unused-token and unused-variant report [IDEA, M]

Build a compiler graph pass that records token/theme/variant references while lowering, then reports configured entries with zero consumers. The report should distinguish “not referenced in this route” from “not referenced in the project.” The existing compiler module graph, grammar registry, and zero receipts provide the inputs. Avoid claiming whole-project reachability until dynamic config access is represented.

### I3. Theme coverage and dark-mode completeness report [IDEA, M]

For each theme key and each route, report which properties have base values, dark/theme clauses, platform clauses, and native support. The clause IR already retains condition sets and theme references (`code/core/web/src/helpers/directStyle.ts:55-67,384-392`; `code/core/style-grammar/src/valueTypes.ts`). A useful first version can be static and warn only on statically known programs.

### I4. Per-route critical CSS and CSS splitting [IDEA, M/L]

Use the lowering plan's per-module CSS arrays and the existing zero artifact ownership to emit route-scoped CSS, shared CSS, and island CSS. The hard part is stable ownership and ordering across server/client builds, not parsing styles. Start with Vite/Next web zero entries, where the artifact contract is already explicit (`code/compiler/metro-plugin/src/zeroSerializer.ts:64-126`; `plans/v3-zero-runtime-mode.md:212-251`).

### I5. Token export to Figma or platform-neutral JSON [IDEA, M]

Export configured tokens, themes, media keys, modifier names, and resolved aliases from the grammar/config view. Add source locations and semantic categories so a design tool can round-trip names without guessing. This should export the normalized config, not scrape JSX. Figma write-back and conflict resolution are a separate L project.

### I6. Inline clause preview in the editor [IDEA, M]

Use source spans plus the grammar's candidate resolver to show the base style and each clause as separate preview rows. A first version can render CSS swatches, spacing boxes, and a condition table in a VS Code hover panel. The existing VS Code bridge only forwards completions today (`code/core/language-service-vscode/README.md:1-12`), so preview UI is new but the parse/diagnostic backend is already present.

### I7. Grammar autocomplete with valid next-condition filtering [IDEA, S/M]

The core already returns cursor completions and modifier-chain candidates (`code/core/style-grammar/src/toolingDiagnostics.ts:615-728`). Package that result as a stable language-service API and add condition-aware filtering, such as offering `@sm` only when the config has a size query and excluding interaction keys from container completion. This is the fastest visible editor win.

### I8. Per-tier compiler debugging and “why did this stay runtime?” [IDEA, M]

Expose the lowering plan's `found`, `lowered`, `flattened`, `styled`, and `bailed` counters with source spans and the exact bailout reason (`code/compiler/compiler-core/src/lower.ts:20-26,318-391`). A dev overlay could show “flattened,” “partial,” “runtime,” or “zero-erased” for a selected element. This would make the compiler's tier model a user-facing advantage rather than an internal concept.

### I9. RSC-safe DOM/zero entry [IDEA, L]

Define a public server-safe component entry whose output is only host JSX, serialized class/style props, and CSS artifact references. Keep eventful and contextful components in explicit client islands. The existing zero server placeholder and theme bridge are a starting point (`plans/v3-zero-runtime-mode.md:899-924`), but the public API, server/client package boundary, and integration matrix still need design and conformance tests.

### I10. Streaming SSR style resource ownership [IDEA, M]

Promote the existing streaming test invariant into an integration feature: each streamed style program is emitted once, contiguously, and associated with the server resource that introduced it. The tests already model the failure that matters (`code/core/core-test/flatValueProgramsStreaming.web.test.tsx:11-24,54-74,194-216`). A route-aware resource manifest is the likely M-sized addition.

### I11. Native capability diagnostics generated from the same matrix [IDEA, S/M]

Generate docs, TypeScript annotations, and development warnings from the grammar's clause capability tables. For example, the same source should explain why `group-hover` is web-only in one component or why a native transform string is dropped. The runtime already emits warnings for unsupported native state/value paths (`code/core/web/src/helpers/directStyle.ts:1712-1729`; `...:1304-1313`).

### I12. Figma/token export plus generated component variant inventory [IDEA, L]

Combine token export with static `styled()` definitions and typed variants to generate a design-system inventory: component name, variant keys, accepted values, defaults, compound combinations, and theme coverage. The static styled type surface and merge implementation are already present (`code/core/web/src/styled.tsx:98-115`; `code/core/web/src/helpers/mergeVariants.ts:33-67`). The difficult part is resolving re-exports and dynamic definitions without overstating completeness.

### I13. Cross-system capability corpus and receipts [IDEA, M/L]

Create byte-identical fixtures for v3, NativeWind, Unistyles, StyleX, and React Strict DOM, with separate web/native/SSR/RSC columns and cold/warm build state. The audit already records that this corpus and compiler-speed harness do not exist (`code/comparisons/V3_BLOG_NUMBERS_GAP_AUDIT.md:80-112`). This is the prerequisite for any honest “faster/smaller than competitor” claim.
